# Next phase: playable characters, abilities and selection

Status: **proposal. No code has been written for this phase.** Every value below is a proposal
for approval, not a decision. Pets and eggs are out of scope for this phase.

## Starting point in the repository (verified)

- `src/shared/Creatures.luau` (generated by `tools/creatures.py`) defines the six cast members:
  Brainy, Blorbo, Glorp, Hjonk, Crusty and Whiffers. Today they are **cell species only**. A
  species is decided by the server when a cell spawns, and it sets the reward (+1, +5 or +10).
  Nothing about them is playable yet.
- The network surface is `BrainrotRemotes/Request`. It accepts only `"Snapshot"`, `"Halo"` and
  `"Steal"`, and rejects any extra arguments. New verbs need an explicit, server-validated design.
- `src/server/Persistence.luau` owns the profile schema (coins, specimens, stats, halo). It sanitises
  every field on load, so new fields must be added there with defaults.
- `RoundMachine` owns score, banked and carried cells. The cell economy must not change because of
  any ability. That is the core invariant of this phase.
- The Halo cosmetic is the only purchase today. Shop and Gear panels already exist and can host a
  character picker.

## Goals

1. Six playable characters. Each has a distinct ability (or ability set) and a cooldown.
2. Character selection and switching. A player holds a loadout of up to **4** characters.
3. Cooldowns that survive switching, so changing character cannot reset a cooldown.
4. All ability effects, ownership, cooldowns and rewards are decided on the server.

## Invariants (must hold, and must be tested)

- **No ability awards or steals Brain Cells.** Carried and banked cells are unchanged by any ability
  or switch. Test: fire every ability in a simulated round and compare cell totals before and after.
- The client sends a *request* (a character slot and an ability verb), never an effect. The server
  checks ownership, phase, cooldown and range before it changes anything.
- A switch or ability cannot run outside `Playing`, or while a player is not participating.
- Cooldowns are stored on the server per player and per character. They are not reset by switching,
  respawning, or starting a new round unless the decision below says so.
- Movement-changing abilities (for example a dash) are applied on the server. `MovementGuard`
  must allow the ability's documented speed and nothing more, and a test must confirm that.
- The existing Stealing rules, stages, persistence and economy are unchanged.

## Decisions needed before implementation

1. **Roster meaning.** Does "3 normal + 1 bonus, max 4" mean that a loadout holds up to 4 of the six
   characters, with 3 normal slots and 1 bonus slot? Or is something else meant? My reading above is
   an assumption.
2. **Unlocks.** How do players get the characters? Options: all free; some free and the rest unlocked
   with earned coins; the secret characters are Robux-only (out of scope until the monetisation phase).
3. **Cooldown persistence.** "Cooldowns persist": does that mean across rounds only, or across
   sessions too? Cross-session cooldowns need new Persistence fields. Cross-round needs only server
   memory.
4. **Ability verbs and remote rules.** The `Request` remote currently rejects arguments. Option A: a
   separate `Ability` remote with one validated integer slot (1–4). Option B: keep one remote and
   relax the argument rule for that verb only. Recommend A.
5. **Roster abilities.** Approve or replace the table above.

## Work breakdown (once approved)

1. `src/shared/Config.luau`: `Characters` (roster, loadout limit 4, cooldowns, durations), with every
   value documented and no sound IDs invented.
2. `src/server/core/CharacterRules.luau` (pure): ownership, loadout validation, switching rules,
   cooldown clock, ability eligibility. No Roblox services. Strict-analysed.
3. `src/server/core/AbilityRules.luau` (pure): effect descriptors (for example `{Kind="Speed", Scale,
   Duration}`), so tests can check effects without Roblox.
4. `src/server/Main.server.luau`: handle `Switch` and `Ability` requests through the rules modules
   only. Apply effects on the server. Reset per-character effects on respawn or round end.
5. `src/server/Persistence.luau`: new fields with defaults and sanitising, if decision 3 needs them.
6. `src/client/Hud.luau` and `Main.client.luau`: a loadout strip with cooldown rings, and a picker
   in Gear. The client only renders server state.
7. `src/client/Audio.luau`: optional ability cues through `Config.Audio.Cues.Ability*`. Silent until
   IDs are configured.
8. Tests: core tests for the rules (loadout limit, switch rules, cooldown persistence across switch
   and respawn, phase gating). Adapter tests for the remote (rejects bad slots, rejects ability
   outside `Playing`, cooldown enforced server-side). The cell-invariance test described above.

## Acceptance for this phase (automated)

- A player can equip up to 4 characters and cannot equip a fifth or a locked one.
- Switching never resets a cooldown.
- Every ability runs on the server, is refused outside `Playing`, and is refused while cooling down.
- Cell totals before and after every ability are identical.
- `tools/check.py` passes with all new tests. The release ZIP is regenerated and hash-checked.
